# LLM rubric evaluation

Open a saved sitting and select **Evaluate LLM rubric**, use guided CLI choice 15, or run `run.cmd cli evaluate-llm RUN_ID [MODEL_PRESET]` against the running backend. The default is the sitting's saved evaluator choice; a browser override or command argument selects a different preset independently of debate agents. Imported sittings use the configured evaluator default. Cloud choices make paid provider calls using existing credentials. Ollama uses the configured loopback model. The deterministic demonstration cannot judge debate quality and is rejected before submission.

Each job captures the committed public transcript, evaluator model, budget configuration, rubric, evaluator prompts and resource hashes. It reads no private agent prompts, grounding or assignments. Public topic/participant/speech/chair evidence is treated as untrusted data. One isolated assessment covers every participant for each stable topic ID. Participants without contributions and empty topics receive explicit insufficient evidence. Empty topics need no model call.

The five metrics are consistency, logical reasoning, responsiveness, relevance and observable rhetorical tactics. They retain independent integer scales; there is no aggregate score or normalization across methods. Higher rhetorical-tactics scores mean more disruption, not better debate quality. None of these metrics predicts private intent or assignment. Consistency requires at least two own contributions. Responsiveness requires cited prior evidence from another speaker followed by the participant's response. Genuine domain review is needed to establish validity.

The shared advanced editor and CLI assets commands expose `config/llm-evaluation.json`, `evaluation/rubric.json`, and `prompts/EvaluatorPrompt.txt`, `EvaluatorCue.txt`, `EvaluatorRepair.txt`. Validation checks all five metric definitions, score anchors, budget limits and prompt placeholders before atomic save. New jobs capture edits; active jobs retain their original resources. Rubric semantics and evidence thresholds can change without recompiling.

Application validation rejects missing/duplicate participants or metrics, unknown fields, fractional/out-of-range scores, unsupported evidence, chair references as speech evidence, cross-topic IDs and responses preceding their cited challenge. An insufficient-evidence assessment has a null score. Structured provider output does not bypass these checks. At most one repair is allowed; call, input/response-character and reserved completion-token budgets also bound work. Refusals, truncation, provider failures and exhausted budgets remain explicit failures.

Completed topics are saved before progress is published. Later failure retains earlier assessments. Cancellation drops the unfinished topic; restart retains results and marks unfinished jobs interrupted without rerunning inference. Reports include implementation version, model settings, rubric/resource hashes, evidence/configuration hashes and each attempt's provider/model, completion status, usage when available, latency and request hash. Raw invalid responses and provider exception text are excluded. No private treatment comparisons are included in blind reports or public transcript exports.

Use `cli jobs`, `cli job JOB_ID`, `cli report JOB_ID report.json` and `cli cancel-job JOB_ID`, or the matching browser controls. Unix uses `sh run.sh cli` with the same arguments.

Software verification uses synthetic providers and an actual loopback HTTP adapter. It tests privacy after sharing an adapter with a privately configured agent, strict evidence/chronology, bounded repair/budgets, explicit refusal, cancellation, retained partial reports, restart, editable resources and CLI/menu/browser parity. The browser fixture labels all synthetic explanations. These checks establish software behavior, not live provider access or research accuracy. No paid evaluator calls were made during this implementation.
